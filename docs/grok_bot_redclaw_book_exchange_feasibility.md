# Grok Bot / RedClaw 书籍包交换技术验证方案

> 状态：技术可行性提案 + 2026-08-31 工程审核。**验证协议可保留；当前载体组合判定为不可行，不得作为产品实现路径。**
>
> 尚未上 Grok Bot 云机，尚未做双公网或正式业务验证。凡未实测项必须保持“未验证”，不得写成已通过。
>
> 文档日期：2026-08-31。审核基于当日 xAI / CloudBase 公开资料、Tomato 现码和 `F:\RedClawDesktop` 当时状态。
>
> 用途：对照审核结论做最小证伪探针，或先做与 P2P 无关的公开分享包。验证通过前，不得把本方案接入 Tomato 正式 Bridge、数据库迁移、发布产物或付费交易链路。不要进入阶段 3。

## 1. 目标与非目标

### 1.1 原提案要验证的流程

原提案希望在不租用传统 VPS、不把完整书籍包长期存入 CloudBase 的前提下，验证：

```text
卖家 Tomato
  → 导出公开分享版书籍包
  → 生成签名资源清单和一次性邀请码
  → 发布目录及在线状态
  → RedClaw DHT/ICE 建立连接
  → P2P 多源分片传输
  → 必要时由 Grok Bot 云端 Linux 节点做超级种子或应用层中继
  → 买家校验分片哈希、整包 SHA-256 和发布者签名
  → 导入 Tomato
```

希望同时验证：

- 卖家离线后，其他用户仍能浏览已经发布的资源信息；
- 至少一个种子在线且可达时，买家能够下载；
- 双方处于严格 NAT 或运营商 CGNAT 后面时，是否有不自建 TURN 的可用兜底；
- Grok Bot 的托管 Linux 虚拟机能否成为常驻目录节点、超级种子或 WebSocket 中继；
- 真实磁盘、后台进程、网络、流量、生命周期和服务条款是否支持该用途。

**审核结论：** 这条端到端流程目前不能作为实现目标。阻塞不在 ICE 细节，而在三块载体都不匹配，且 Tomato 还没有「公开分享版书籍包」。后续若仍做探针，目的是尽快证伪 A/B 类，不是为集成做准备。

### 1.2 非目标

本轮不实现，审核后仍禁止：

- 微信支付、自动分账、退款、担保交易或财务账本；
- DRM 或“买家解密后仍绝对无法复制”的承诺；
- 用 AI 模型逐片处理或转发书籍包；
- 未经授权的内容上传、版权内容分发或公开索引；
- 在未验证网络能力前部署标准 TURN；
- 将 xAI API Key、CloudBase Key、私钥或管理员凭据写入客户端、仓库或日志；
- 把本方案接入 `app/lib/`、`web_ui/src/`、正式 Web Bridge 或发布产物；
- 把 Grok Bot 当 VPS，或把现有 RedClaw 桌面串流栈当文件 swarm 复用。

## 2. 工程审核结论（2026-08-31）

### 2.1 总评

作为验证协议，本文第 4～11 节的纪律合格，甚至偏严：控制面与数据面分离、目录可见不等于可下载、DHT 不能当全站商品列表、SHA-256 不能当身份、双 CGNAT 没有中继就会失败、AI 不得碰书籍正文、单项 `connected` 不算交付成功。这些约束继续有效。

作为“用 Grok Bot + RedClaw 做书籍包交换”的产品技术路径，**当前不可行**。更稳妥的先验不是「条件可行、去实测」，而是：

- **A 类公网直达超级种子：先验很低，官方资料下应默认失败。**
- **B 类隧道/WSS 中继：网络形态比 A 合理，但条款、共享计算机、国内可达和 token 成本仍可能直接落入 D。**
- **C 类目录/巡检：相对最接近 Grok Bot 产品形态，仍要过条款，且解决不了交付。**
- **真正缺的第一块不是 DHT 或 ICE，而是可公开分享的书籍包格式。**

一句话：用 Grok Bot 省 VPS、用 RedClaw 省文件协议，这两笔账目前都算不平。先把本机迁移包收成真正的分享包，再用最普通的方式传文件；P2P 云种子是以后的可选优化，不是现在的可行性结论。

### 2.2 已核对的事实（静态审计，非云机实测）

以下为只读核对，**未**登录 Grok 云机、未做外部入站探针、未跑 RedClaw Linux 构建。

#### Grok Bot 是账号级 AI 工作站，不是种子机

官方能确认：

- 托管 Linux VM、`/workspace` 持久化、浏览器/文件系统/终端；
- 静态**出口** IP；
- 关闭本地 App 后，**Bot turn / routine** 可在云端继续；
- Kill/Reset/Update 后持久盘可保留；进程以非 root 运行；
- 计费含周额度，超出按模型和 token。

官方**没有**确认，因而不能当设计前提：

- 独立公网入站 IP、自定义 TCP/UDP 端口、TURN 端口范围；
- 磁盘上限、持续传输带宽、常驻守护进程 SLA。

会直接削弱「超级种子」叙事的公开条款：

1. 静态出口 IP ≠ 入站可达。`listen()` 成功或看到本机端口都不算。
2. [计算机说明](https://docs.x.ai/grok-bot/computer-and-apps) 写明：临时目录、**手动安装的软件包**、未提交的应用状态都应视为可被替换。镜像更新会重建计算机。
3. [FAQ](https://docs.x.ai/grok-bot/faq) 写明会话会因计算机重建或**网络地址变化**而掉线。这与「72 小时 Peer ID + 固定端口」相反。
4. 同一账号下所有 Bot 共用浏览器登录、文件和命令行凭据。加密分片、节点私钥、邀请 token 会和其他 Bot 的邮箱/云控制台 Cookie 住在同一台机器上。不能把这台机器当成多租户 CDN。
5. [Custom MCP Tunneling](https://docs.x.ai/grok/connectors/custom-mcp-tunneling) 的方向是 **Grok 去连用户本机 MCP**，不是从 Grok VM 对外提供 WSS 入口。不得再把该页当作 Grok 入站依据。免费 ngrok/cloudflare URL 每次重启变化，只能用于探针。
6. 用 AI 做安装/巡检/崩溃恢复，等于把「VPS 运维」写成持续 token 消耗；VM 一重建还要再装一遍。
7. 把消费级 AI 工作站当成长期文件分发或应用层 TURN，很大概率不属于产品意图用途。服务条款未实测通过前，可单独把方案打进 D 类。

#### RedClaw 是 Windows 远程桌面，不是文件交换栈

`F:\RedClawDesktop` 在 2026-08 的主线是：

```text
机器码 → DHT 信令 → ICE → Host 桌面采集 → H.264/HEVC → Controller 解码播放
```

| 原提案假设 | 当时代码/文档事实 |
|---|---|
| Linux headless 种子 | Windows-first；vcpkg triplet 为 `x64-windows`；依赖 `cppwinrt`、NVENC/QSV/AMF、Qt GUI |
| 文件分片 / 续传 / 多源 | **M08 明确推迟**，直到 P0 画面闭环完成 |
| 复用 DataChannel 传大文件 | 媒体通道是零重传、丢弃过时帧的 `redclaw-media-v1`，与可靠文件传输语义相反 |
| DHT 发布资源清单 | 现有 DHT 是桌面会话 rendezvous，不是内容 provider record / 文件 swarm |
| 装到 Grok Linux | 没有 Linux 构建目标 |

即便 Grok 云机网络奇迹般可用，也还要另写一套 Linux 文件协议。那时 RedClaw 只剩下「也有 DHT/ICE」，不值得为 Tomato 书籍交换去改。Tomato 还要覆盖 Android + 运营商 CGNAT，而这是 NAT 穿透最差的一端；RedClaw 移动端同样未做。

#### Tomato 只有本机迁移包，没有公开分享包

现有 `BookTransferService` / `series.export` / `series.import` 是本机迁移 zip，不是可上架内容：

- 会打进 `learning_records`、跟读录音、`api_cache_entries`（TTS/绘本等付费缓存）；
- UI 文案是「选择书籍迁移包」；
- 有资源 SHA-256，没有发布者签名、邀请码、过期或公开/私有分级；
- 导入侧没有压缩炸弹、最大解压尺寸、路径穿越的专项门槛（本文第 6、9 节写了，代码里还没有）。

绘本原图是 `2560×1440`，一章最多 12 景，再加 TTS、歌曲后，一本完整书到数百 MB～数 GB 是合理量级。先定义「公开分享版」比先做 P2P 更关键：至少要剥掉学习记录和用户录音，并单独决定绘本/TTS 缓存能不能随包走（那是付费生成物，还有版权源文本问题）。

Tomato 当前是无自建后端的本地客户端。除本文外，仓库里没有 CloudBase 实现。若用 CloudBase 做卖场浏览，那是新产品形态（账号、目录、投诉、下架），不是现有「书库 / 创作中心 / 练习中心 / 设置」上的一个传输按钮。

### 2.3 角色可行性（审核后）

| 候选角色 | 原判断 | 审核后判断 | 说明 |
|---|---|---|---|
| 标准 TURN | 未证实 | **默认不可用** | 官方只公布静态出口 IP；除非外部入站 UDP 实测通过 |
| 公网超级种子（A） | 条件可行 | **先验很低** | 手册安装包会被镜像更新清掉，地址会变 |
| WSS/隧道中继（B） | 条件可行 | 网络上比 A 合理，产品上仍可能直接 D | 条款、共享计算机、国内可达、token 成本 |
| 目录/巡检（C） | 较可行 | 相对最接近官方形态 | 仍要过条款；解决不了交付 |
| 权威订单/支付 | 不建议 | 保持不建议 | AI 云机不能做财务信任根 |
| 用现有 RedClaw 当数据面 | 隐含可复用 | **当前不能复用** | 无 Linux 目标，无文件协议 |
| CloudBase 当中继/大文件 | 未作为主路径 | **禁止** | 见第 2.4 节 |

原第 2.1 节「Grok Bot 可作为候选 AI 管理型云端节点、条件可行」对超级种子偏乐观。保留其技术谨慎（文件保留 ≠ 进程/端口/IP 永存；不能仅凭能装软件下结论；隧道不是纯 P2P；AI 不得进数据面），但先验改为 **C 类候选，A/B 需先被证伪而不是被集成**。

### 2.4 系统性风险

- **中国网络路径。** Tomato 用户和文档语境在国内，Grok/xAI 基础设施在国外。DHT bootstrap、STUN、到 Grok 的长连接 WSS 都可能被干扰或高延迟。若 CloudBase 只做目录、数据面却走美国 AI VM，这是产品网络设计问题，不是后期优化项。
- **「不租 VPS」并不更简单。** 落地形态会变成 Grok 订阅 + token + CloudBase 目录 + 隧道厂商 + 自研节点 + NAT 探测。比一台有公网的 Linux，或「目录 + 对象存储签名 URL」更碎。省掉的是月租，加上的是不可控生命周期。
- **CloudBase 不能当数据面。** 控制面只存小数据是对的。云函数 WebSocket 常见限制是单消息 256KB、单连接约 128KB/s；若把中继放到 CloudBase WS，1 GiB 传输门槛会直接失败。**禁止把 CloudBase 当中继或书籍包存储。**
- **合规不是附录。** 跟读录音、学习记录绝不能进公开包；绘本/TTS 是云 API 付费产物；Alice 等原著有版权。P2P 加密 swarm 降低的是云存储账单，不降低分发责任。邀请码私密交换仍然是内容分发平台。
- **Android 买家是主场景之一。** 桌面 Windows 打洞成功不能外推到手机 CGNAT。验证矩阵若只写「两台不同公网设备」而不包含移动端，不能宣称产品可用。

连接顺序那 9 步是教科书 ICE，对远程桌面有意义；对「偶尔交换一本约 1GB 的教育内容包」过重。多数失败会出在「没有稳定公网入口」和「没有可公开的包」，不是卡在 QUIC 打洞。

### 2.5 若目标是用户之间交换书籍

P2P 解决的是发现和 NAT。Tomato 现在缺的是可分享的包格式和一条无聊的交付通道。建议顺序与 P2P 方案解耦：

1. **先做公开分享包**（可仍走现有 zip，但必须改语义）：去掉学习记录和录音；资源清单 + 整包哈希，以后再加签名；导入继续走现有校验并补上 zip 炸弹/路径穿越。这一步不依赖 Grok、RedClaw、CloudBase。
2. **交付先用已有渠道**：U 盘、网盘、微信文件，或国内对象存储的短时签名 URL。卖家离线可下载，对象存储比 DHT 更擅长。
3. **只有包格式和版权策略清楚了**，再决定要不要目录。目录用 CloudBase 小数据是合理的；那就是承认有后端，不要再包装成纯 P2P。
4. **不要为这个需求改 RedClaw，也不要把 Grok Bot 当 VPS。** 若以后真要做种，用独立 Linux 文件节点（或成熟的 BitTorrent/HTTP 分片），跑在自己控制的主机上。

### 2.6 如何使用本文其余章节

- 第 3 节是原提案架构，**仅供对照，不是当前推荐实施设计。**
- 第 4～6、8～11 节的验证纪律、安全边界和 A/B/C/D 门槛仍然有效；探针必须遵守。
- 第 7、12 节已按审核收窄：阶段 0 的目的是证伪，不是铺开 `tomato-exchange-node`。
- 后续 Agent 不得把「条件可行」或第 3 节框图当成已批准的产品架构。

## 3. 原提案架构（仅供对照，当前不推荐实施）

### 3.1 控制面与数据面分离

```text
控制面
  资源目录 / Presence / 邀请码 / 订单状态 / 路由选择
       │
       ├─ 可选 CloudBase 小数据
       └─ DHT 签名记录和客户端目录缓存

数据面
  Tomato / RedClaw 客户端
       │
       ├─ 首选：IPv6 / 端口映射 / ICE 直接传输
       ├─ 次选：从其他可达种子下载
       └─ 兜底：Grok 云机 WSS 中继或加密超级种子
```

若将来另选真实主机做数据面，控制面/数据面分离仍然成立。CloudBase 如果使用，只保存用户、商品目录、邀请、Presence 和订单等小数据，不保存完整书籍包，也不得承担中继。

### 3.2 Grok 云机内部结构（原设想）

```text
Grok Bot（AI 运维控制面）
  ├─ 安装、升级和回滚
  ├─ 查看脱敏日志与健康状态
  ├─ 定时清理过期缓存
  └─ 崩溃告警和受控恢复
          │
          ▼
tomato-exchange-node（确定性 Linux 守护进程）
  ├─ identity：持久化 Peer ID / 公钥身份
  ├─ catalog：签名资源清单缓存及索引
  ├─ presence：在线状态与能力声明
  ├─ seed-store：加密分片存储与配额
  ├─ transport：DHT / ICE / QUIC / TCP / WSS
  ├─ relay：受限的 Tomato 协议中继，禁止任意代理
  └─ health：指标、审计事件和自动恢复
```

禁止将书籍包内容发送给大模型上下文。Bot 只管理守护进程，守护进程直接读取文件和网络数据。这一条即使放弃 Grok 数据面也仍然成立。

审核补充：不要在阶段 0 设计这七个子模块。一个出站 heartbeat 加一次外部端口探测，通常就够把 A 类关掉。

## 4. 资源浏览与做种模型

这些规则在任何交付通道上都成立，不依赖 Grok 或 RedClaw。

### 4.1 目录可见不等于文件可下载

卖家上线时发布一份签名资源清单。清单复制到 DHT 临近节点、目录节点或其他客户端本地缓存。卖家下线后资源仍可显示，但必须标记真实可用性：

```text
目录状态：可浏览
在线种子：0
下载状态：等待卖家或其他种子上线
```

只有至少一个通过可达性验证的种子在线，才显示“可立即下载”。对象存储签名 URL 未过期且可 GET，也视为可达种子。

### 4.2 DHT 的搜索边界

DHT 适合按已知键查找 Peer、资源清单或内容提供者，不天然支持“列出全网所有书籍”和任意全文搜索。至少选择一种目录层：

1. CloudBase 或其他小数据目录：可靠性最高，完整书包仍不进该目录存储；
2. DHT 分类/时间分片索引，例如 `catalog/英文绘本/2026-W36`；
3. Gossip 广播后由每个客户端写入本地 SQLite 搜索索引。

纯 P2P 方案必须有稳定引导节点、索引分片上限、TTL、去重、撤销和垃圾信息治理。不能通过遍历整个 DHT 来实现商品列表页。当前产品若需要列表页，应承认需要后端目录，而不是用 DHT 硬凑。

### 4.3 建议资源清单

示意字段如下，最终 schema 必须在实现前单独评审。公开分享包本身尚不存在，清单不能先于包格式定稿。

```json
{
  "schemaVersion": 1,
  "listingId": "stable-random-id",
  "packageCid": "content-address",
  "packageSha256": "hex",
  "packageSize": 123456789,
  "title": "example",
  "language": "en-zh",
  "category": "picture-book",
  "publisherPeerId": "peer-id",
  "publisherPublicKey": "encoded-public-key",
  "createdAt": "RFC3339",
  "expiresAt": "RFC3339",
  "revision": 1,
  "signature": "publisher-signature"
}
```

不要在公开清单中存储手机号、微信号、邮箱或家庭网络地址。联系和预约使用 Peer ID、公钥和端到端加密消息。

### 4.4 种子可达性分级

| 等级 | 能力 | 可否作为“立即下载”依据 |
|---|---|---|
| A | 公网 IPv6 或公网 IPv4 直接可达 | 可以 |
| B | UPnP IGD / PCP / NAT-PMP 映射成功且外部探针通过 | 可以 |
| C | ICE 或 BitTorrent 式打洞实测成功 | 可以，但需记录有效期 |
| D | 只能出站、无法被连接 | 不能单独作为可靠种子 |
| R | 通过 WSS/Relay 可达 | 可以，但必须显示中继路径和限额 |
| S | 对象存储或其它 HTTP 签名 URL 可 GET | 可以，但必须显示过期时间；这不是 P2P |

多种子可以提高找到 A/B/C/R/S 节点的概率，但如果所有 P2P 种子都是 D 级，种子数量再多也不能凭空建立数据通道。

## 5. 连接策略与 TURN 边界

若仍做 P2P 探针，连接顺序如下。对书籍交换产品，第 9 步（临时云存储离线交付）应视为比第 8 步更优先的产品路径，而不是最后才想起的兜底。

```text
1. 同一局域网直连
2. 公网 IPv6
3. 公网 IPv4 / 手动端口转发
4. UPnP IGD / PCP / NAT-PMP 自动映射
5. ICE + STUN UDP 打洞
6. QUIC/TCP 打洞或 ICE-TCP
7. 通过公共 Relay 协调 DCUtR/类似打洞，再升级到直连
8. 应用层 WSS 中继（不默认假设中继在 Grok 云机上）
9. 临时云存储或其它 HTTP 离线交付
```

“做种下载”解决文件来源和多源可用性，不自动解决 NAT。DHT 解决发现，不转发文件。双方及所有种子都处于严格 NAT/CGNAT 后面时，要么接受连接失败，要么引入某种公网中继或对象存储。

若某节点只支持出站 HTTPS/WSS，可让两端都主动建立出站 WSS：

```text
卖家客户端 ──出站 WSS──► 中继 ◄──出站 WSS── 买家客户端
```

这种方式能绕过大多数 NAT，但本质上是应用层 TURN。它可以避免部署标准 TURN 协议，却没有消灭服务器、流量和滥用治理成本。中继主机必须是自己控制、条款允许、国内可达的机器；**不要默认写 Grok 云机。**

## 6. 书籍包与交易安全边界

### 6.1 完整性与身份

最低要求：

- 公开分享包不得包含学习记录、跟读录音或其它个人练习数据；
- 每个分片有序号、长度和哈希；
- 完成后校验整包 SHA-256；
- 发布者对资源清单和整包哈希做数字签名；
- 邀请码是有过期时间、用途和使用次数限制的 capability token；
- token 必须防重放，并绑定 listing、买家或交易会话；
- 导入前检查格式版本、路径穿越、压缩炸弹和最大解压尺寸。

SHA-256 只能证明内容没有变化，不能证明发布者身份或交易授权，因此不能省略数字签名和授权 token。现有迁移包只有资源哈希，不满足公开分发。

### 6.2 加密与缓存

若使用第三方超级种子，只保存端到端加密后的包或分片：

```text
本地公开分享包
  → 随机内容密钥加密
  → 加密分片上传种子节点
  → 买家完成授权后取得密钥
  → 下载、合并、校验、解密、导入
```

目录节点、DHT 节点和中继节点不应持有买家明文密钥。日志只记录 ID、hash、长度、时长、状态和错误阶段，不记录书籍正文、密钥、token 或完整私人路径。Grok 共享计算机尤其不能持有明文密钥或未加密包。

### 6.3 无法由技术完全解决的事项

- 买家获得明文内容后，客户端技术不能保证其永远不复制；
- 支付、退款、分账和争议处理仍需要可信业务规则；
- 公开交易必须处理版权、用户上传内容、隐私、投诉和下架；
- 绘本图、TTS、歌曲等付费生成物随包分发，不会因为走了 P2P 就变成无责任；
- Grok Bot 或 P2P 不会自动消除这些产品与合规责任。

## 7. Cursor 验证范围和工作方式

### 7.1 先调查，不先改正式代码

按审核后的顺序工作。目标是证伪或确认第 2 节判断，不是铺开产品架构：

```text
确认 Tomato 公开分享包是否存在（静态代码即可）
  → 静态审计 RedClaw：Linux 目标、M08 文件协议、媒体通道语义
  → 在隔离目录建立最小探针（不要编译完整 RedClaw 上云）
  → 验证 Grok 云机：heartbeat、磁盘、出站、外部入站、条款
  → 得到 A/B/C/D 分类
  → 只有 A/B 未被证伪，才考虑独立文件协议原型
  → 最后才判断是否值得设计产品集成（当前预期：不值得沿原载体推进）
```

- 不因 DHT 找到记录就宣称数据链路成功；
- 未真实运行的测试必须标记为未验证；
- 不得把 MCP 隧道文档、静态出口 IP 或单机 `listen()` 写成入站成功。

### 7.2 RedClaw 能力（静态审计结论，构建复核仍有效）

2026-08-31 只读审计已经给出否定结论，见第 2.2 节。若代码此后发生变化，必须从当前树重新验证，不能使用本审核代替新证据：

- 是否已有可用的 Linux 构建目标；
- 是否存在无界面 Host/Seeder 入口；
- DHT 后端用途是会话 rendezvous 还是内容 provider；
- ICE candidate 类型、STUN 策略、IPv6、ICE-TCP、QUIC 支持情况；
- UPnP/IGD、PCP、NAT-PMP 的实际支持；
- 是否支持文件分片、断点续传、多源下载和哈希树（当时为 M08 未做）；
- 是否存在 WebSocket 应用层 transport；
- 当前 DataChannel/媒体传输代码能否复用于大文件，还是需要独立文件协议（当时媒体通道为零重传丢帧）；
- Linux 构建依赖、许可证和发布产物大小。

如果 RedClaw 只有 Windows GUI 或桌面串流协议，不得假设能够直接安装到 Grok Linux，也不得为此去移植整棵桌面栈。

## 8. Grok 云机验证矩阵

阶段 0 只做能证伪 A/B 的最小集。不要先做 5 GiB / 20 GiB，除非入站或稳定隧道已经通过，并且用户明确授权可能产生的费用。

### 8.1 环境与权限

记录但不得泄露敏感数据：

- Linux 发行版、内核、CPU 架构；
- 当前用户、是否有 `sudo`、包管理器和编译工具；
- `/workspace` 与其他挂载点容量、可用空间和文件系统；
- 内存、CPU 配额、进程和文件描述符限制；
- 是否允许安装二进制、共享库和用户级服务；
- 时间同步、DNS、IPv4、IPv6 和普通 HTTPS 出站；
- 账号计划、可见使用额度和明确的服务限制；
- 服务条款是否允许长期文件分发、中继或常驻守护进程。

产出环境快照时对公网 IP、用户名、组织名和路径做脱敏。

### 8.2 后台进程生命周期

用无业务数据的 heartbeat 守护进程验证：

1. 启动后持续写入单调时间、进程 ID 和启动 ID；
2. 结束当前 Bot turn、关闭本地 Grok App 后检查进程；
3. 快速门槛为连续 30 分钟，候选门槛为 24 小时，试运行门槛为 72 小时；
4. 人工终止进程，验证监督器能否自动恢复；
5. 在获得用户明确授权后才执行云机重建/Reset/Update 测试；
6. 重建后检查持久化文件、Peer ID、**手动安装的二进制是否还在**、缓存索引和服务是否自动恢复。

如果只能依赖 Bot 周期性重新启动程序，不能宣称是常驻种子。官方已提示手动安装包可被镜像更新替换，重建测试是 A 类的关键否决项。

### 8.3 网络与公网入站

分别验证：

- TCP 出站；
- UDP 出站；
- IPv6 全球地址是否存在及是否真正可达；
- STUN 返回的映射地址和 NAT 行为；
- 外部独立主机到 Grok 云机高位 TCP 端口；
- 外部独立主机到 Grok 云机 UDP 端口；
- 端口是否在空闲、重启或云机重建后保持；
- 是否存在固定入站地址、允许的端口范围和连接时长限制；
- 从国内网络访问该入口的可达性和延迟（若用户在国内）。

入站探针必须要求随机 nonce 并限时关闭，不能暴露无鉴权 shell、文件目录或通用代理。

只有外部独立网络成功连接，才算入站可达；`listen()` 成功、看到本机端口或得到静态出口 IP 都不算。

### 8.4 反向隧道和 WSS

若公网入站失败，再验证反向隧道。隧道必须是从 Grok 云机**主动出站**连到自己控制的入口，不能把「Grok 连接用户本机 MCP」那份文档当成已有入站能力。

记录：

- 隧道 URL 是否固定；
- 是否支持 WebSocket；
- 连续连接时长；
- 单连接和总并发；
- 最大帧、空闲超时和重连行为；
- 1 GiB 及以上持续传输是否限速或中断；
- 隧道服务的流量、用途和服务条款是否允许该场景；
- 国内网络访问该隧道 URL 是否稳定。

免费临时 URL 每次重启变化，只能用于探针，不能作为生产地址。通过隧道后应将结果分类为“隧道超级种子/中继”，不能分类为“公网直达种子”。

### 8.5 存储、流量和配额

使用确定性生成的非敏感伪随机测试数据，不使用全零稀疏文件代替真实传输。A/B 未通过前不要做到扩展档。

| 阶段 | 建议大小 | 目的 |
|---|---:|---|
| 快速 | 256 MiB | 验证基本分片、续传和哈希 |
| 基线 | 1 GiB | 验证常见大书包和长连接 |
| 压力 | 5 GiB | 验证磁盘、配额、限速和恢复 |
| 扩展 | 20 GiB | 仅在授权及前述通过后执行 |

每次记录：

- 发送端和接收端 SHA-256；
- 已传输字节、重复字节和失败分片；
- 吞吐中位数、P95、总时长；
- CPU、内存、磁盘、网络和文件描述符峰值；
- 中断位置、续传起点和重复开销；
- 账号用量变化、限速、异常和可能费用（含 Grok token，不只是带宽）。

### 8.6 DHT、ICE 和真实双网络

至少使用两台处于不同公网/运营商网络的真实设备。若产品包含 Android，其中一端必须是移动 CGNAT，否则不得宣称产品网络可用。

1. 节点发布短 TTL 的签名测试清单；
2. 买家从 DHT 或目录索引取得清单；
3. 验证 Peer ID、签名和版本；
4. 记录双方候选类型和最终选中路径；
5. 依次验证公网直连、端口映射、打洞和 WSS 中继；
6. 传输 1 GiB 测试包并比对 SHA-256；
7. 主动中断网络后恢复并续传；
8. 卖家下线，验证剩余种子或 HTTP 交付能否独立完成；
9. 中继/超级种子下线，验证其他买家种子能否继续交付。

`DHT fetch hit`、`remote description applied`、`connected` 或 `channel_open` 任一单项都不足以证明文件交付成功。必须有真实接收字节、完整分片、整包哈希和导入前验证结果。

## 9. 安全与故障注入测试

至少覆盖：

- 篡改资源清单后签名验证失败；
- 篡改单个分片后只重传该分片；
- 错误整包 SHA-256 禁止导入；
- 过期、撤销和已使用 token 被拒绝；
- 未授权 Peer 无法枚举或下载私人资源；
- 文件名路径穿越、符号链接和绝对路径被拒绝；
- 压缩炸弹和超出声明解压尺寸被拒绝；
- 中继只连接已认证 Tomato Peer，不能代理到任意互联网地址；
- 公开包中出现学习记录或跟读录音视为失败；
- 日志不出现内容密钥、邀请码、正文、Cookie、Authorization 或完整私有路径；
- 进程崩溃、磁盘满、网络抖动、DHT 记录过期和时钟漂移均有明确错误状态；
- 旧版本客户端、包 schema 和撤销记录有显式兼容或拒绝策略。

## 10. 通过门槛与结论分类

### A：公网直达超级种子

同时满足：

- Linux headless 节点可重复构建和部署（不要求这是 RedClaw）；
- 后台进程至少连续 72 小时；
- 持久化 Peer ID 和缓存经受受控重启/**镜像 Update/Reset** 验证，手动安装的二进制仍可恢复；
- 外部独立网络能够稳定连接 TCP，并按所选协议验证 UDP 或 QUIC；
- 国内网络路径若属于产品场景，也必须可达；
- 1 GiB 和 5 GiB 传输、续传、SHA-256 均通过；
- 磁盘、流量、**服务条款**和账号政策允许该用途。

此时该主机可作为候选超级种子；标准 TURN 是否可用仍由 UDP 入站和端口范围单独决定。按 2026-08-31 公开资料，Grok Bot 达到 A 的先验很低。

### B：隧道/WSS 超级种子或应用层中继

公网入站失败，但稳定 WSS/反向隧道、长连接、大文件、续传和条款均通过。此时可作为中继兜底，但必须承认数据经过第三方隧道，记录流量并设置严格配额。Grok 共享计算机和 token 计费未解决前，即使传输成功也可以因安全/成本判 D。

### C：目录与自动化节点

进程或网络不适合长期数据传输，但持久化磁盘和例行任务稳定。此时只承担资源清单镜像、健康检查和通知，不承担书籍包。这是 Grok Bot 相对最接近的合法形态。

### D：不采用

出现任一项即停止将 Grok Bot 作为数据节点：

- 后台进程随 turn、额度或空闲状态频繁终止；
- 无稳定连接入口且隧道不允许或不稳定；
- 磁盘/带宽上限不公开或实测不足；
- 云机重建导致身份、缓存、**已安装服务**无法可靠恢复；
- 服务条款不允许长期文件分发、中继或常驻守护进程；
- 无法建立可审计的安全和限额边界；
- 与同一账号其它 Bot 共享计算机，无法隔离密钥和登录态；
- 国内产品路径不可达或延迟不可用。

按审核，原载体组合在得到反向实测证据之前，应按 **倾向 D（数据面）/ 至多 C（目录）** 处理，而不是按「条件可行的 A/B」规划集成。

## 12. 推荐阶段路线

### 阶段 0：零产品改动（当前唯一建议执行的技术验证）

- 静态确认公开分享包不存在、RedClaw 不能当文件 swarm；
- 若用户授权：在 Grok Linux 运行 heartbeat、磁盘、出站和外部入站探针；
- 得到 A/B/C/D 分类。预期是关掉 A，并可能因条款/共享计算机关掉 B。
- 不要设计 `tomato-exchange-node` 七模块，不要移植 RedClaw。

### 与 P2P 解耦的产品任务（优先于阶段 1～3）

- 定义公开分享包：剥离学习记录和录音；补哈希/后续签名；导入侧补 zip 炸弹和路径穿越；
- 用 U 盘、网盘、微信文件或对象存储签名 URL 交付；
- 版权与付费生成物策略单独评审。
- 这些任务可以在 Tomato 内进行，但仍须用户明确要求改代码；它们不是本 P2P 方案的实现。

### 阶段 1：最小超级种子原型（仅当阶段 0 得到 A 或稳定 B，且条款通过）

- 只使用生成测试数据；
- 单一发布者、单一买家；
- 固定 Peer ID、签名清单、分片和断点续传；
- 节点必须是自己控制的主机，不默认 Grok；
- 不接支付，不改 Tomato 正式数据库。

### 阶段 2：双网络和多种子

- 两个真实外网，其中一端覆盖 Android CGNAT（若产品包含 Android）；
- 一个种子、一个普通客户端；
- 测试卖家离线和种子切换；
- 收集真实直连率和中继率。

### 阶段 3：受限产品试点

**当前不要进入。** 只有在技术、条款、版权、安全和公开分享包全部通过后，并且载体已不是「Grok 当 VPS + RedClaw 当 swarm」时才重新评审。

若那时仍要试点：

- CloudBase 只保存必要小数据，禁止当中继；
- 中继默认关闭，按连接失败显式启用；
- 设置用户级、资源级和节点级流量上限；
- 保留完全关闭外部节点的回退路径。

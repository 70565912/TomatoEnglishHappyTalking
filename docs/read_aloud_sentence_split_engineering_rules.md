# 英文朗读分句工程迭代约束

状态：长期执行

本文件只规定分句算法的工程、验证和迭代方式。语义规则、评分顺序和最终输出约束以
[`read_aloud_sentence_split_spec.md`](read_aloud_sentence_split_spec.md) 为唯一来源。

## 1. 三项同级验收

每轮候选必须同时报告并比较：

1. 质量：代理依据统一规范判定的“不支持切法”数量和占比；
2. 性能：同机、同输入、同构建模式交替运行的中位耗时；
3. 结构：功能逻辑量、重复路径、主体流程复杂度、职责边界和文件规模。

候选的不支持切法必须少于最近一次已接受版本；高于最近版本即失败，不得合入。速度提升和结构精简
与不支持切法减少同等重要。任何显著性能回退必须否决；代码原则上应越来越精简，只有切法质量优异
或速度提升显著时才允许小幅功能代码增量。

实验分支的不支持切法已经降到 0 后，后续轮次不再要求不可能的“少于 0”，而是必须保持 0，并至少
严格改善一个次级指标（朗读长度分布、emergency 数、速度、功能代码量或模块复杂度），同时不得让
其它硬门禁回退。归零只是继续优化的质量下限，不自动等于可以替换生产最佳版本。

结构精简不机械比较全仓总行数。按稳定职责拆分巨型文件、删除重复逻辑、把主体流程收敛为清晰调用
属于精简；跨文件必需的 import、类型和接口胶水不算功能膨胀。仅搬移代码或增加转发层而没有降低
复杂度，不算精简。

## 2. 通用性与架构

- 生产算法不得读取 Alice、Willows、章节号、完整句子或词语白名单，不得按书、章节或个例分流。
- 目标架构是一次事实构建加一次有界 DAG 求解；不得按新增规则重复全文扫描、递归重算修复窗或逐候选
  再跑完整 DP。
- 核心按事实构建、候选与规则评分、有界求解、结果审计等稳定职责模块化。同一事实只有一个权威计算
  位置；不得把全部逻辑继续塞进单个巨型文件。
- 每次改动只处理一个可说明的机制，删除被替代路径；禁止靠层叠特例和无限递归推进。
- 在统一 DAG 重构完成前，若新增候选进入整句排序会扩散重排，过渡实现只可在最近已接受路径的单个
  `>20` 稳定段中增加规范明确支持的边界；不得删除、替换或移动任何既有稳定边界，不得调用递归整句
  求解，也不得把该兼容层视为最终架构。每个此类入口都必须有句面廉价预筛，空路径不得分配候选列表；
  后续统一求解重构必须把它吸收到一次事实构建和一次有界 DAG 中并删除兼容层。

## 3. 分级验证

小改先跑固定的 Alice + Willows 代表章节和固定回归，不得每次无差别跑两本书全量。代表集必须覆盖：

- 当前待修缺陷及其相邻边界；
- 已批准边界和不应改变的负例；
- 1–5 词短块、8–16 词舒适区、17–20 词标点区、21–30 词积极切分和 30 词硬上限；
- 引语、括号、标点切点、安全句法切点和错误依存树。

长度与句法采用分级风险比较，不写成非黑即白的互斥规则。尤其 `21–24` 词允许 KEEP 或切分：句法用于
帮助选择朗读换气点，不要求每个块脱离上下文成为独立语法句，也不得成为默认保留长句的理由。
长度触发后必须先比较合格原文标点；无合格标点时才进入句法成分边界。句法实现必须区分成分内部和
成分之间：允许完整主语｜谓语、谓语｜完整宾语，禁止拆开主语/谓语/宾语/表语自身的紧密组成部分；
不得仅凭 `nsubj` / `obj` crossing 把原文标点或完整成分边界判为不合格。标点停顿的优先级不由
“分块能否独立成为完整语法句”决定；多个标点候选再比较标点强度、短块和长度，但不得跨过已有句号、
分号、冒号或破折号去选择更弱逗号。

累计形成候选或准备发布时，再运行 Alice + Willows 两书全量门禁。测试范围不得为制造性能收益或隐藏
回归而缩小。代理按规范自行判断，不把逐句人工审核作为前置条件。

性能基准至少覆盖普通短句、Alice E02 长括号和 Alice/Willows 的长引语或多候选章节；采用 AOT 编译、
交替运行和中位数，保留原始样本。显著回退的候选直接失败，噪声较大时增加轮次，不凭单次最好值放行。

## 4. Git 与记录

- 每轮尝试使用独立 `codex/` 分支和聚焦提交；基线、接受版本和失败路径均可回退。
- 局部优化连续受同一旧框架牵制时，可以在独立分支从统一规范重新实现完整框架，并在分支内连续迭代；
  中间检查点只和该分支最近一次已接受检查点比较。只有质量、性能、结构三项都胜过生产最佳版本后，
  才做一次性全量对比并提出替换；在此之前，对生产最佳版本的检查只用于确认冻结门禁与量纲，不得
  因局部差异反复把新框架拉回旧实现。未满足最终单次事实构建、单次有界求解和模块职责门槛前不得合并。
- 每轮在分句基线/重构记录中写明假设、修改、代表输入、输出变化、不支持数量与占比、耗时、结构变化
  和接受/拒绝结论。
- 失败实现必须从生产代码撤回，但保留文档与 Git 记录，避免重复尝试同一路径。
- 每次修改先以最近一次已接受版本为比较基线；只有三项门槛通过后，候选才可成为下一轮基线。

## 5. Flutter 工具前置检查

分句测试也遵守仓库通用 Flutter 锁规则：每次调用 Flutter 前通过 `tools/run_flutter.ps1` 或已接入公共
guard 的构建脚本检查 `flutter.bat.lock`、`lockfile` 的独占访问和 SDK cache 可写性。检查失败立即停止，
不得直接调用 `flutter.bat` 等待锁循环，也不得把删除锁文件当成默认解法。
